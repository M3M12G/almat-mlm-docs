# Платежи и выплаты

## Приём платежей (покупки)

- Прямая интеграция с REST API эквайринга (варианты для РК: Epay/Halyk,
  Kaspi Pay, CloudPayments).
- Комиссия обычно 2.5–3.5% с транзакции, интеграционного взноса как правило нет.
- **Вебхуки обязательны** — статус платежа обновляется асинхронно, не полагаться
  на синхронный ответ фронта.
- **Идемпотентность** — критично. Один и тот же вебхук может прийти дважды
  (retry со стороны платёжного провайдера) — обработка должна быть
  идемпотентной по `transaction_id` провайдера, иначе риск задвоить начисление
  бонусов с одной покупки.

## Выплаты партнёрам (вывод средств)

Отдельный модуль от приёма платежей — другая специфика:
- KYC-минимум (хотя бы паспортные/ИИН данные для выплаты)
- Лимиты на вывод (минимальная сумма, частота)
- На пилоте — **ручное/полуручное подтверждение админом**, не автоматические
  массовые выплаты (снижает риск при первом запуске)
- Уточнить в банке заранее: массовые выплаты физлицам могут требовать отдельного
  договора — согласование может занять 2-4 недели, планировать заранее

## 2FA для вывода средств

Обязательно перед выводом — минимизирует риск захвата аккаунта и вывода чужих
средств.

## Идемпотентность — общий принцип

Каждая финансовая операция (покупка, начисление бонуса, заявка на вывод) должна
иметь уникальный идентификатор операции, и обработчик должен проверять, не была
ли эта операция уже обработана, прежде чем создавать новые записи в
`bonus_transactions` / `withdrawal_requests`.

## Открытые вопросы к банку/эквайрингу (см. также `07_open_questions.md`)
- Актуальные комиссии Epay/Kaspi Pay для юрлиц на момент запуска
- Требования к массовым выплатам физлицам (нужен ли отдельный договор)
- Сроки поступления средств на расчётный счёт (влияет на кэш-флоу выплат)
