# ADR-0003: Bonus rules as config, not code

## Контекст

Compensation plan — 5 механизмов (Direct, Unilevel, Matching, Rank, Leadership
Pool) с процентами, порогами, уровнями и ранговыми условиями. Маркетинг будет
менять цифры без желания ждать деплой. Хардкод в C# приведёт к постоянным
переписываниям BonusEngine и риску расхождения staging/prod.

## Решение

Правила живут в таблице `bonus_rules` с полем **`config_json` (JSONB)**. Код
engine читает активное правило по `code` / периоду и интерпретирует конфиг.
Изменение процента (например, 4-й реферал 35% вместо 30%) — правка данных
(админка / SQL), не релиз нового билда.

Тот же принцип для ранговых условий: `ranks.required_condition_json`,
`leadership_pool_points` — данные.

## Альтернативы

| Вариант | Почему не взяли |
|---|---|
| **Хардкод в C# / switch** | Любое изменение плана = деплой; сложно A/B и откат |
| **Отдельный DSL/скрипты** | Избыточная сложность для пилота |
| **Feature flags только** | Не покрывают структуру уровней/рангов |

## Последствия

- ✅ Comp plan меняется без деплоя (в рамках схемы конфига)
- ✅ Аудит: кто менял правило — через admin + `audit_log`
- ⚠️ Версионирование `active_from` / `active_to` обязательно для пересчётов
- ⚠️ Агент **не хардкодит** проценты/пороги в коде — только чтение `config_json`
- ⚠️ До закрытия `docs/07_open_questions.md` BonusEngine не реализовывать
- 📄 Детали: `docs/03_bonus_engine.md`, `db/schema.sql` (`bonus_rules`)
