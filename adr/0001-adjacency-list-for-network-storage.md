# ADR-0001: Adjacency List for network storage

## Контекст

Сеть партнёров — Unilevel («солнечные лучи»): неограниченная ширина, без лимита
глубины, без циклов. Обход **вверх** (Direct / Unilevel Bonus, ≤10 уровней)
нужен часто; обход **вниз** — для ранговых условий. Спонсор по умолчанию
назначается один раз при регистрации (смена — редкий/админский кейс). Нужна
модель хранения в PostgreSQL без graph-БД.

## Решение

Хранить дерево как **Adjacency List**: `users.sponsor_id → users.id`, индекс
по `sponsor_id`. Обход вверх/вниз — `WITH RECURSIVE`. Агрегаты команды
(`total_team_volume` и т.п.) — материализованные, инкремент вверх при покупке;
полный down-scan только в batch-сверке (**Quartz** job).

## Альтернативы

| Вариант | Почему не взяли |
|---|---|
| **Closure Table** | Лишняя таблица и запись при каждом insert; нет частых move/reparent |
| **Materialized Path** | Строковые LIKE-обходы хуже индексируются; path-перезапись при редком move |
| **Nested Sets** | Пересчёт lft/rgt при любом insert — дорого при росте сети |
| **Neo4j / graph DB** | Избыточно для линейного Unilevel без частого реструктурирования |

## Последствия

- ✅ Дешёвый ancestor walk для bonus (линейно по глубине, не по ширине)
- ✅ Простая схема, EF Core + raw CTE
- ⚠️ Циклы через N звеньев — проверка в коде при смене `sponsor_id` (не только CHECK)
- ⚠️ Down-обход на лету запрещён — только агрегаты / batch
