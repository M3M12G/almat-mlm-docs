## Адендум 2026-09-21 (влияние авторизованных наблюдений §1.6)

Уточнения к модели, не меняющие выбор стека:
- **Wallet — два суб-счёта** (deposits/commissions) с правилом «сперва пополнения». Проектировать `Wallet` с раздельными балансами и явным порядком списания; проводки — append-only ledger со статусами pending→commission→reserved→paid. Это усиливает выбор **rich domain** для кошелька (§3) и **иммутабельность финансов** (§6).
- **BonusAccrual.type** = {referral, matching, **level2**, career, pool} — «Уровневый 2%» отдельный тип; расчётчик (Rewards-модуль, §4) обрабатывает 4–5 типов.
- **Цикл — фиксированные календарные окна, глобальный** → Quartz-джоба закрытия периода по календарю (§11), не per-partner планирование.
- **Структура — cap 10 линий** → закрытая глубина упрощает closure-table/materialized-path (§5); запросы квалификации ограничены 10 уровнями вверх (важно для «Уровневого 2%»).
- **Активация = оплаченный пакет** → флаг активности партнёра как предусловие всех начислений (гейт в Rewards-движке).
- **Кабинет = `?section=` + fallback на default** → SSR-роутинг с whitelist секций и дефолтом, не 404 (§2).
- **2FA** присутствует → раздел безопасности в Identity-модуле (§8), приоритет повышен.

## 1. Общая форма системы

**Решение:** Модульный монолит (ASP.NET Core) с чётко разделёнными модулями (feature slices) + отдельные фоновые воркеры. Kafka как шина событий между модулем-издателем начислений/кошелька и воркерами.

- **Зачем:** продукт цельный (единая БД партнёров/кошелька/начислений), сильная транзакционная связность финансов. Монолит даёт простые транзакции ACID и низкую операционную сложность на старте.
- **Проблема:** финансовая консистентность (баланс, начисления, сторно) плохо ложится на распределённые транзакции; ранний микросервис = распределённый монолит + сага-боль.
- **Альтернативы:** (а) микросервисы с самого начала; (б) serverless-функции; (в) чистый монолит без модульных границ.
- **Почему выбрано:** модульный монолит = быстрый time-to-market + сохранение границ для будущего выделения сервисов (кошелёк — первый кандидат). Соответствует принципу «fewest moving parts».
- **Confidence: high.**

**Выделение в сервисы (post-MVP):** кошелёк/блокчейн-воркер и расчётчик бонусов — естественные швы. Заложить их как модули с событийным интерфейсом уже в MVP.

## 2. Frontend Architecture

**Решение:** Server-Side Rendering (Razor Pages/MVC в ASP.NET Core) + progressive enhancement на ванильном TypeScript. **Не** SPA.

- **Зачем:** требования NFR-01 (SSR, работа без JS), SEO (SEO-01..03), доступность (NFR-03). Контент-ориентированная витрина.
- **Проблема:** SPA дал бы избыточную сложность (гидратация, дублирование валидации, SEO-проблемы) для преимущественно статического контента.
- **Альтернативы:** (а) Next.js/Nuxt SSR; (б) React SPA + отдельный API; (в) Blazor Server; (г) Blazor WASM.
- **Почему выбрано:** SSR на Razor держит один язык/стек с backend, минимум JS, лучший baseline SEO/a11y/perf. Клиентские виджеты (фильтр каталога, калькулятор, маска телефона, копирование, табы) — изолированные progressive-enhancement скрипты, как в оригинале.
- **Confidence: high** для SSR; **medium** для точного выбора Razor vs Next (зависит от команды).

**Кабинет и админка:** те же Razor-страницы за авторизацией; островки интерактива (дерево структуры, дашборд рангов) — отдельные TS-модули. **Confidence: medium** (для сложного дерева структуры возможен локальный SPA-островок — решается на дизайне UI).

**Стилизация/сборка:** CSS с токенами (light/dark), сборка через Vite/esbuild для TS-бандлов. **Confidence: medium.**

## 3. Backend Architecture

**Решение:** ASP.NET Core, организация по **feature slices** (Vertical Slice) с **CQRS через MediatR**; тонкие контроллеры/страницы диспатчат команды/запросы; `Result<T>` для ожидаемых отказов, `ProblemDetails` (RFC 9457) для HTTP-ошибок; `IExceptionHandler` на границе.

- **Зачем:** требования FR (много разнородных операций), ERR-04 (ожидаемые отказы как результат), единый формат ошибок (API-08). Совпадает с рабочими конвенциями команды.
- **Проблема:** «толстые» контроллеры и смешение чтения/записи усложняют финансовую логику и тестирование.
- **Альтернативы:** (а) классические сервисы/репозитории без CQRS; (б) Clean Architecture с отдельными слоями Application/Domain; (в) transaction script.
- **Почему выбрано:** Vertical Slice + MediatR даёт локальность изменений (fewer feature slices за задачу), pipeline-behaviors (валидация, логирование, транзакции, аудит) в одном месте. Согласуется со скилами `dotnet-mediatr`, `dotnet-api-design`, `dotnet-error-handling`.
- **Confidence: high** (для этой команды/стека).

**Модель домена:** rich domain для финансового ядра (Wallet, BonusAccrual, PayoutRequest) — инварианты в сущностях; anemic-подход допустим для контентных модулей (News, Product) . **Confidence: medium.**

## 4. Services / Modules

**Решение:** модули (bounded contexts) внутри монолита:

| Модуль | Ответственность | Изоляция |
|---|---|---|
| **Catalog** | Товары, категории, документы товара | own schema |
| **Content** | Новости, страницы, обучающие материалы | own schema |
| **Identity** | User, аутентификация, сессии, восстановление | own schema |
| **Partner** | Partner, структура (дерево), пакеты, реф-коды | own schema |
| **Rewards** | BonusAccrual, ранги, периоды, расчёт/сторно (MLM-движок) | own schema |
| **Wallet** | Кошелёк, TRON-адреса, транзакции, выплаты, курс | own schema |
| **Commerce** (POST) | Корзина, заказы, checkout | own schema |
| **Legal** | Документы, редакции, согласия | own schema |
| **Support** | Обращения, уведомления | own schema |
| **Admin** | Админ-функции поверх модулей (RBAC) | cross-cutting |
| **Platform** | Общее: файлы, локализация, аудит, конфиг | cross-cutting |

- **Зачем:** границы модулей = будущие швы для сервисов, ограничение blast radius изменений.
- **Проблема:** без границ монолит превращается в «большой шар грязи», особенно опасно смешение финансов с контентом.
- **Альтернативы:** плоская структура по техническим слоям; сразу микросервисы.
- **Почему выбрано:** модули по домену + разные схемы БД → низкая связность, кросс-модульное взаимодействие только через события Kafka или явные внутренние интерфейсы (не прямые FK между схемами).
- **Confidence: high** для набора модулей; **medium** для точных границ Rewards/Wallet (могут слиться).

## 5. Database

**Решение:** PostgreSQL (single primary), одна БД, **схема на модуль** (`catalog.`, `partner.`, `wallet.`…). EF Core для команд/записи и сложного маппинга; Dapper для тяжёлых read-запросов (дерево структуры, отчёты).

- **Зачем:** ENT-* / REL-* реляционны; финансы требуют ACID; локализация ПД в РК (NFR-10).
- **Проблема:** финансовая консистентность и рекурсивные запросы структуры плохо ложатся на NoSQL.
- **Альтернативы:** (а) MySQL; (б) SQL Server; (в) NoSQL (Mongo); (г) отдельная БД на модуль.
- **Почему выбрано:** PostgreSQL — рекурсивные CTE для дерева, `numeric` для денег, JSONB для гибких полей (condition_json ранга), надёжные транзакции. Схема-на-модуль сохраняет границы без оверхеда множества БД. Совпадает со скилами `dotnet-data-access`, `dotnet-ef-migrations`.
- **Confidence: high.**

**Денежные типы:** `numeric(18,2)` для ₸, `numeric(36,6)`+ для USDT; никогда float. **Confidence: high.**

**Дерево структуры:** materialized path или closure table для быстрых поддеревьев, а не рекурсия на каждый запрос. **Confidence: medium** (зависит от глубины/ширины; для MVP — recursive CTE, оптимизация post-MVP).

**Миграции:** EF Core migrations, review сгенерированного SQL, никогда не править применённые. **Confidence: high.**

## 6. Entities (проекция на persistence)

**Решение:** сущности из ENT-01..23 маппятся 1:1 на таблицы соответствующих схем; переводы (Product/News) — отдельные таблицы `*_translation` с (entity_id, locale).

- **Зачем:** i18n RU/KK (NFR-04), версионирование документов (FR-36).
- **Проблема:** хранение мультиязычного контента и исторических редакций.
- **Альтернативы:** (а) JSONB-колонка с локалями; (б) отдельные таблицы переводов; (в) дубли строк на язык.
- **Почему выбрано:** отдельные таблицы переводов — индексируемость и целостность; JSONB для нерегулярных полей (rank condition). Финансовые записи (WalletTransaction, BonusAccrual) — **append-only/immutable**, статус меняется через новые записи/поля, не перезапись сумм. **Confidence: high.**

**Ключевые инварианты на уровне БД:**
- Уникальный индекс `WalletTransaction(network, contract, txid, event_index)` — идемпотентность зачисления (FR-29, SEC-08). **Confidence: high.**
- Уникальный `Partner.referral_code`, `Wallet.tron_address`. **Confidence: high.**

## 7. API

**Решение:** внутренние endpoint'ы форм (SSR-POST с CSRF) для MVP; приватный REST/JSON API кабинета — post-MVP; интеграционные коннекторы (курс, блокчейн) — внутренние.

- **Зачем:** API-01 (формы+CSRF), API-04 (приватный REST post-MVP), API-08 (единый формат ошибок).
- **Проблема:** преждевременный публичный API = поддержка контракта без потребителей.
- **Альтернативы:** (а) API-first + SPA; (б) GraphQL; (в) gRPC для внутренних.
- **Почему выбрано:** SSR-формы покрывают MVP без API-контракта. Когда появится мобильное/партнёрское потребление — добавить versioned REST (`/api/v1`) с OpenAPI. Ошибки — `ProblemDetails`. **Confidence: high** для MVP-подхода; **medium** для будущего REST vs GraphQL.

**Идемпотентность финансовых POST** (выплаты): idempotency-key + серверная дедупликация (API-07). **Confidence: high.**

## 8. Authentication

**Решение:** cookie-based session auth (ASP.NET Core Identity или кастомный store), Argon2id для паролей, secure/HttpOnly/SameSite cookie, антифорж-токены на форму.

- **Зачем:** AUTH-01..03, наблюдаемый паттерн оригинала (session cookie + CSRF).
- **Проблема:** stateless JWT в браузере уязвим (XSS, отзыв), избыточен для SSR-сайта.
- **Альтернативы:** (а) JWT в cookie; (б) OAuth/OIDC-провайдер (Keycloak/IdentityServer); (в) magic-link.
- **Почему выбрано:** серверные сессии = мгновенный отзыв, простота, соответствие SSR. Восстановление пароля — одноразовый токен с TTL (AUTH-06). Внешний IdP (Keycloak) — кандидат post-MVP при росте (SSO админов, 2FA). **Confidence: high** для MVP.

**2FA (TOTP)** для админов/финоператоров — post-MVP (AUTH-09). **Confidence: medium.**

**Хранилище сессий:** Redis (см. §10) для горизонтального масштабирования. **Confidence: high.**

## 9. Authorization

**Решение:** RBAC — роли Guest/Partner/Admin + под-роли (ContentModerator, FinanceOperator, SuperAdmin); policy-based авторизация в ASP.NET Core; явная проверка на каждом защищённом действии; авторизация ресурса (partner видит только свои данные).

- **Зачем:** UR-01..06, AUTH-05, SEC-07 (least privilege).
- **Проблема:** горизонтальный доступ (партнёр к чужому кошельку/структуре) — критичный риск в финансах.
- **Альтернативы:** (а) простые роли без policy; (б) ABAC/претензии; (в) внешний авторизационный сервис (OPA).
- **Почему выбрано:** policy-based + resource-based checks покрывают роли и владение данными без оверинжиниринга. Финансовые действия — отдельные policy с аудитом. **Confidence: high.**

## 10. Caching

**Решение:** Redis как (1) distributed session store, (2) кэш курса USD/KZT и справочников, (3) rate-limit counters; HTTP-кэш/ETag для публичных страниц; кэш каталога с инвалидацией по событию.

- **Зачем:** NFR-05 (perf), NFR-08 (масштаб), устойчивость к сбою внешних API (курс кэшируется).
- **Проблема:** повторные запросы к БД/внешним API на публичных страницах; сессии в памяти не масштабируются.
- **Альтернативы:** (а) in-memory кэш (не для multi-instance); (б) CDN edge-cache; (в) без кэша.
- **Почему выбрано:** Redis — стандарт для shared-state в k8s-деплое. **Финансовые данные не кэшируются** (баланс всегда из БД). Курс кэшируется с TTL до следующего обновления. **Confidence: high.**

⚠️ **Явное правило:** баланс кошелька, доступные суммы, статусы выплат — только из источника истины (БД), без кэша. **Confidence: high.**

## 11. Background Jobs

**Решение:** отдельные worker-процессы (ASP.NET Core `BackgroundService` / hosted workers, отдельный deployment). Планировщик: Quartz.NET (cron-джобы) для курса/периодов; consumers Kafka для реактивных (сторно по возврату). Idempotent handlers, retry+DLQ.

| Джоба | Тип | Механизм |
|---|---|---|
| JOB-01 Поллинг TRON | периодический | Quartz + идемпотентная запись |
| JOB-02 Курс НБ РК | cron (по расписанию) | Quartz |
| JOB-03/04 Расчёт бонусов | по закрытию периода | Quartz + событие |
| JOB-05 Сторнирование | реактивный | Kafka consumer |
| JOB-06 Email | очередь | Kafka consumer + retry/DLQ |
| JOB-07 Генерация TRON-адреса | при регистрации | синхронно или Kafka |

- **Зачем:** JOB-01..10; финансовые расчёты и внешние опросы не должны блокировать web-запросы.
- **Проблема:** долгие/периодические операции в web-процессе = таймауты, нестабильность.
- **Альтернативы:** (а) Hangfire; (б) cron в контейнере + CLI; (в) внешний оркестратор (Airflow); (г) всё в web-процессе.
- **Почему выбрано:** отдельные воркеры + Quartz + Kafka дают изоляцию, ретраи, масштаб. Согласуется со скилом `dotnet-masstransit-kafka`. Hangfire — альтернатива, но Kafka уже нужна для событий (см. §13), не плодим брокеры.
- **Confidence: high** для архитектуры; **medium** Quartz vs Hangfire (оба валидны; Hangfire проще для cron, Kafka всё равно для событий).

**Поллинг блокчейна** — критично идемпотентный: unique-constraint не даёт двойного зачисления даже при повторной обработке. **Confidence: high.**

## 12. File Storage

**Решение:** S3-совместимое объектное хранилище (MinIO on-prem / облачный S3) с непредсказуемыми ключами; выдача через приложение (приватные) или presigned-URL/CDN (публичные). Метаданные файла — в БД.

- **Зачем:** FILE-01..06 (PDF документов, изображения товаров).
- **Проблема:** хранение бинарей в БД/на диске пода не масштабируется и теряется при рестарте.
- **Альтернативы:** (а) файлы в PostgreSQL (bytea); (б) локальный диск + PVC; (в) облачный blob (Azure Blob/GCS).
- **Почему выбрано:** S3-совместимое = стандарт, presigned-URL, CDN-готовность, независимость от подов. MinIO для локальной/on-prem РК-локализации. **Confidence: high.**

**Валидация:** mime/размер/расширение + антивирус-скан (ClamAV) для загрузок (FILE-03, SEC-05). **Confidence: medium** (антивирус — post-MVP допустимо).

## 13. Search

**Решение:** MVP — клиентский фильтр каталога/новостей (как в оригинале) + серверная фильтрация/пагинация админ-списков средствами SQL с индексами. Post-MVP — серверный поиск каталога (PostgreSQL full-text/`tsvector`). Nice-to-have — выделенный движок (OpenSearch) при большом объёме контента.

- **Зачем:** SFS-01..07.
- **Проблема:** клиентский фильтр не масштабируется на большой каталог; полнотекст на SQL LIKE медленный.
- **Альтернативы:** (а) сразу Elasticsearch/OpenSearch; (б) Meilisearch; (в) только SQL.
- **Почему выбрано:** объём номенклатуры мал (единицы-десятки товаров) → выделенный поисковый движок — оверинжиниринг для MVP. PostgreSQL FTS покрывает post-MVP. OpenSearch — только если контент/новости вырастут. Принцип «skip → stdlib → dep». **Confidence: high** для MVP; **medium** для порога перехода на OpenSearch.

## 14. Messaging

**Решение:** Apache Kafka (MassTransit v8) как шина доменных событий между модулями и воркерами: `WalletCredited`, `OrderPaid`, `OrderRefunded`, `BonusAccrued`, `RankAchieved`, `PayoutRequested`. Idempotent consumers, DLQ, outbox-паттерн для атомарной публикации.

- **Зачем:** JOB-05 (реактивное сторно), развязка модулей, будущее выделение сервисов, NFR-08.
- **Проблема:** прямые синхронные вызовы между модулями создают связность и каскадные сбои; потеря событий при падении.
- **Альтернативы:** (а) RabbitMQ; (б) in-process MediatR notifications; (в) БД-outbox без брокера; (г) без асинхронности.
- **Почему выбрано:** Kafka — durability, реиграбельность (важно для финансовых событий/аудита), совпадает со скилом `dotnet-masstransit-kafka`. **Outbox** гарантирует «БД-транзакция + публикация» атомарно (критично для консистентности начислений). **Confidence: high** для событийного подхода; **medium** Kafka vs RabbitMQ (Kafka лучше для реиграбельности/аудита, но тяжелее в эксплуатации — оправдано финансовым доменом).

⚠️ Для MVP при малой нагрузке допустим in-process + outbox без Kafka, но заложить интерфейсы под брокер. **Confidence: medium.**

## 15. Observability

**Решение:** структурированные логи (Serilog → OpenSearch/Loki), метрики (OpenTelemetry → Prometheus + Grafana), трейсинг (OTel → Jaeger/Tempo), health-checks (`/health/live`, `/health/ready`), алерты на финансовые аномалии.

- **Зачем:** NFR-11, LOG-04..06, ERR-08/09; финансы требуют наблюдаемости (всплеск сторно/выплат — сигнал).
- **Проблема:** без наблюдаемости инциденты кошелька/начислений невидимы до жалоб.
- **Альтернативы:** (а) только логи; (б) APM-вендор (Datadog/AppInsights); (в) ELK-only.
- **Почему выбрано:** OpenTelemetry — вендор-нейтральный стандарт, готов к k8s. Корреляция запрос↔событие↔джоба через correlation-id. **PII/секреты не логируются** (LOG-05, SEC-03). **Confidence: high** для подхода; **medium** для конкретных бэкендов (Loki vs OpenSearch — по инфре).

**Аудит** (LOG-01..03, immutable) — отдельный append-only store в БД, не путать с техническими логами. **Confidence: high.**

## 16. Deployment

**Решение:** контейнеры (multi-stage Dockerfile), GitLab CI/CD (build → test → scan → package → deploy), окружения dev/test/prod, Helm-чарты, деплой в Kubernetes. Blue-green/rolling для web, отдельный релиз воркеров.

- **Зачем:** NFR-08/09, соответствие скилу `dotnet-ci-k8s`.
- **Проблема:** ручной деплой = нестабильность, нет отката.
- **Альтернативы:** (а) VM + systemd; (б) PaaS (App Service); (в) serverless.
- **Почему выбрано:** k8s даёт масштаб, self-healing, единый деплой web+workers+инфра. GitLab CI — по конвенциям команды. Миграции БД — отдельный job/init-container перед rollout, с ревью SQL. **Confidence: high.**

**Секреты:** Kubernetes Secrets + внешний Vault/Key Vault (SEC-03); никогда в образе/репозитории. **Confidence: high.**

## 17. Kubernetes Requirements

**Решение:**

| Компонент | Тип | Заметки |
|---|---|---|
| web (SSR) | Deployment + HPA | stateless, sticky не нужен (сессии в Redis) |
| workers | Deployment(s) | по типу джоб; блокчейн-поллер — single-active (leader election) |
| PostgreSQL | StatefulSet/managed | primary+replica, PVC, бэкапы |
| Redis | StatefulSet/managed | сессии, кэш, rate-limit |
| Kafka | StatefulSet/managed | durable, топики с репликацией |
| MinIO/S3 | managed/StatefulSet | объектное хранилище |
| Ingress | nginx-ingress | TLS-терминация, security-заголовки, rate-limit |

- **Зачем:** реализация NFR-08/09, изоляция stateful/stateless.
- **Проблема:** блокчейн-поллер при нескольких репликах даст дубли обработки; stateful-компоненты нельзя в обычный Deployment.
- **Альтернативы:** managed-сервисы (RDS/MSK/ElastiCache) vs self-hosted в кластере.
- **Почему выбрано:** managed для stateful (надёжность/бэкапы) предпочтителен, но **локализация ПД в РК** (NFR-10, SEC-09) может требовать on-prem/локального облака — тогда StatefulSet в кластере. Поллер — **leader election** (single-active), чтобы не дублировать зачисления (страхует поверх unique-constraint). Health/liveness/readiness обязательны. Resource requests/limits, NetworkPolicy (изоляция wallet-воркера), PodDisruptionBudget.
- **Confidence: high** для структуры; **medium** managed vs self-hosted (зависит от требований локализации РК).

## 18. External Integrations

| Интеграция | Назначение | Наблюдаемо? | Решение | Confidence |
|---|---|---|---|---|
| **TRON blockchain** | чтение USDT TRC-20 Transfer-событий | заявлено в документе | Коннектор через провайдера (TronGrid/собственная нода) + anti-corruption layer; провайдер за интерфейсом | high (нужность), **low** (конкретный провайдер) |
| **Курс НБ РК** | USD/KZT для конвертации | наблюдаемо (RSS-ссылка) | Клиент с кэшем+ретраем; при недоступности — «ожидание курса», без резервного курса (FR-34) | high |
| **Email (SMTP/провайдер)** | восстановление, уведомления | частично (форма восстановления) | Абстракция отправки + очередь; провайдер (SES/SMTP) за интерфейсом | medium |
| **Фиатный платёжный шлюз** | оплата заказов | не подключён в оригинале | Post-MVP, за интерфейсом; выбор по рынку РК | low (не определён) |
| **SMS** | OTP/уведомления | не обнаружено | Nice-to-have | low |
| **Антивирус (ClamAV)** | скан загрузок | наше требование | Post-MVP | medium |

- **Зачем:** реализация FR-27..34, NTF-*, интеграции из requirements §6.
- **Проблема:** прямая зависимость от внешних API = хрупкость; блокчейн/курс могут падать.
- **Почему выбрано:** каждая внешняя система за **anti-corruption layer / интерфейсом** → заменяемость провайдера, тестируемость (моки), устойчивость (ретраи, circuit breaker). Блокчейн-провайдер намеренно абстрагирован — снаружи не определён, не хардкодим. **Confidence: high** для паттерна изоляции.

⚠️ **Kastodial-ключи TRON:** генерация/хранение приватных ключей — самый чувствительный узел. Решение: шифрование at-rest (envelope encryption через KMS/Vault), доступ только у wallet-воркера, изоляция NetworkPolicy, аудит доступа. **Confidence: high** для необходимости; **medium** для конкретного KMS (зависит от инфры РК).
