# Спецификация функционального аналога — Wellness/MLM платформа

> Функциональная спецификация аналога (на основе `docs/reverse-engineering.md`).
> Внешний вид и контент **не** копируются — описывается функциональная модель.
> Домен: e-commerce витрина wellness/БАД + MLM-партнёрская программа + кастодиальный крипто-кошелёк (USDT/TRON) с учётом в тенге.
> Юрисдикция по умолчанию: Республика Казахстан (RU/KK).
> Дата: 2026-09-21.

## Адендум 2026-09-21 (уточнения по авторизованному кабинету, §1.6 reverse-engineering)

Подтверждённые наблюдением факты, уточняющие требования ниже:
- **FR-19..23 (MLM):** типов начисления **четыре** — Referral, Matching, **Уровневый бонус 2%** (отдельный тип, покрыть новым **FR-19a**), Карьерная премия; Global Pool — вероятно с ранга Gold+. Цикл Referral — **фиксированные календарные границы, 10 дней, глобальный**. Начисления/прогресс идут **только при активированном аккаунте + оплаченном действующем пакете** (усиливает FR-26).
- **FR-27..33 (Кошелёк):** в модели **два раздельных баланса** — «Пополнения» (из USDT) и «Комиссии» (начисления), расход сперва из пополнений (новый **FR-31a**). Статусы начисления: «ожидает» → комиссионный баланс → резерв (выплата) → выплачено.
- **FR-16 (Структура):** глубина ограничена **10 линиями**; поле спонсора (upline); реф-код = `FV`+zero-padded id партнёра.
- **ENT-08 Wallet:** два баланса + timestamp сверки; **ENT-11 BankDetails** — карта+счёт, отображение маскированное `•••• NNNN`; **ENT-12 BonusAccrual.type** = {referral, matching, level2, career, pool}.
- **AUTH-09 (2FA):** присутствует в оригинале как раздел «Безопасность и 2FA» → поднять приоритет с `[NTH]`/P2 до **P1**.
- **ERR (роутинг кабинета):** секции через `?section=`, неизвестная секция → **fallback на profile**, не 404 (новый **ERR-10**).
- **Материалы:** прогресс чек-листа — **localStorage per-partner**, не сервер; файлы публикуются после двуязычной проверки владельцем (модерация контента).

## Легенда

- **Приоритет:** `[MVP]` — минимально жизнеспособный продукт · `[POST]` — после MVP · `[NTH]` — nice-to-have.
- **ID-префиксы:** PS (scope), UR (roles), UJ (journeys), FR (functional), NFR (non-functional), PG (pages), CMP (components), ENT (entities), REL (relationships), API, AUTH, FILE, NTF (notifications), JOB (background), SFS (search/filter/sort), ERR (errors), LOG (audit/log), ADM (admin), SEC (security), SEO, AN (analytics).
- Каждое требование атомарно и трассируемо по ID.

## Сводка приоритизации

**MVP (запуск платформы в тестовом/информационном режиме):**
публичная витрина + каталог + регистрация/вход + кабинет партнёра + MLM-движок (Referral/Matching/Career) + кошелёк TRON/USDT с выплатами + правовой центр + базовая админка + безопасность/аудит финансов + базовый SEO/i18n.

**Post-MVP (запуск продаж и расширение):**
корзина/checkout/заказы + фиатные платежи + Global Pool + автоквалификация рангов + обучающие материалы + расширенные уведомления + приватный API + sitemap/structured data + веб-аналитика.

**Nice-to-have:**
2FA, SMS, публичный партнёрский API, A/B-тесты, CDN, реконсиляция кошельков, bug bounty.

## Открытые вопросы / зависимости (для уточнения до реализации)

- OQ-01: Точная схема шага 2 регистрации (генерация username, требования к паролю) — не наблюдалась снаружи.
- OQ-02: Провайдер блокчейн-данных (собственная нода / TronGrid / обозреватель) и модель push vs poll.
- OQ-03: Регламент выплат (минимум, комиссии, налоговые удержания, календарь).
- OQ-04: Точные условия квалификаций рангов и правила Global Pool в расчётном периоде.
- OQ-05: Целевой технологический стек (SSR-фреймворк, БД, очереди) — определяется командой.

*Спецификация функциональная и стек-агностична; детали реализации определяются на этапе проектирования.*
