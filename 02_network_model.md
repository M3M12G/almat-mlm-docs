# Модель хранения сети покупателей

## Топология
Unilevel ("солнечные лучи"): неограниченная ширина (сколько угодно личных
приглашённых у одного спонсора), без ограничения глубины, без циклов.

## Выбор структуры хранения: Adjacency List

Решение зафиксировано в `docs/adr/0001-adjacency-list-for-network-storage.md`.

Кратко (а не Closure Table / Materialized Path / Nested Sets):
- Нет операций "перемещения ветки" (в отличие от бинара с ребалансировкой).
- Нет ограничения на количество детей у узла.
- Дерево растёт только вниз, узлы не переставляются местами.
- Обход **вверх** (нужен для Direct/Unilevel Bonus, максимум 10 уровней) —
  дешёвая линейная операция независимо от ширины дерева.

## Защита от циклов

```sql
ALTER TABLE users ADD CONSTRAINT no_self_sponsor CHECK (id != sponsor_id);
```

Этот constraint ловит только прямой цикл (A→A). Цикл через несколько звеньев
(A→B→C→A) constraint на уровне БД не поймает — нужна проверка в коде **при
любом назначении/смене sponsor_id**: обход цепочки предков от предполагаемого
спонсора вверх до корня; если в цепочке встретился сам приглашаемый — блокировать
операцию.

**Важно**: если бизнес-правило — "спонсор назначается один раз при регистрации
и никогда не меняется" (см. `07_open_questions.md`), риск цикла практически
нулевой, но проверку всё равно оставить как safety net на случай админских
правок вручную.

## Обход вверх (для Direct Bonus, Unilevel Bonus)

Дешёвая операция, глубина фиксирована (макс. 10 уровней), не зависит от ширины
дерева. См. `db/queries_recursive.sql`.

## Обход вниз (для ранговых условий — состав команды по рангам)

Потенциально дорогая операция при широком и глубоком дереве одновременно.
**Не считать на лету.** Подход:
- Материализованный агрегат на каждом пользователе (`total_team_volume`,
  `team_rank_composition`), обновляемый **инкрементально вверх по цепочке
  предков** при каждой покупке — не пересчётом всего поддерева вниз с нуля.
- Полный пересчёт всего дерева — только фоновой job (**TickerQ**), редко,
  как сверка/защита от рассинхрона.

## Leadership Pool — отдельный случай

Единственный расчёт, где нужны данные обо **всей компании**, а не о ветке
одного пользователя. Считается фоновой job (**TickerQ**) раз в месяц по всей
таблице `purchases` за период — не через обход дерева.

## Масштаб

Такая модель на PostgreSQL спокойно тянет десятки/сотни тысяч пользователей без
необходимости в специализированных graph-базах (Neo4j избыточен для линейного
Unilevel без частого переструктурирования).
